# 複数サービス向けバナー作成Webアプリ｜統合要件定義書

版：0.3-draft／2026-11-05　位置づけ：開発前の要件基線（実装方式を確定する文書ではない）

設計レビューVer.0.2：本書のユーザー要求は維持する。相反・未確定の実装規則は`16_設計決定台帳.md`および`17`～`20`の仕様契約で明確化。設計提案をユーザーの明示要件として扱わない。

## 1. 目的と対象
pixivFANBOX等へ投稿するときに使うバナーを、初回のテンプレート設計以降は可能な限り「メイン画像・テキストの入力→バリエーション選択→出力先選択→調整→一括書き出し」で作成する。似たデザインを別サイズ・別サービスへ派生させる。iOS SafariとAndroid Chromeを主要対象、PC主要ブラウザにも対応する。モバイルでのタッチ操作を第一級の操作方法とする。

従来のVer.0.1、Ver.0.2追補、その後の「優先表示／除外領域」「相対構図保持」「角度自動調整許可」を一体化した。曖昧点は`08_未決定事項・リスク台帳.md`に記録。網羅的な機能IDは`09_要件トレーサビリティ.csv`を正本とする。

### 1.1 操作フロー
1. ベーステンプレートを作る。サービス別の表示を確認し、文字、画像枠、ラベル、装飾、レイヤー・効果を設定して保存する。
2. ラベル色・背景・装飾色・アイコングリフ・効果をカテゴリや公開区分に応じて切り替えるバリエーションを作る。ベース自体は保持する。
3. 投稿ごとの新規プロジェクトを作り、テンプレート・バリエーションを選択し、タイトル・日付・連番・画像などを入力する。
4. 出力先を複数選び、キャンバスを切り替えてセーフエリア・構図を確認する。個別調整した場合は当該プロジェクト・当該出力先にのみ保存する。
5. PNGを一括書き出しする。後でプロジェクトを再開し、バリエーションを変えたり、画像を差し替えて再出力できる。

### 1.2 保存と変更の原則
- Template（ベース）とVariant（見た目差分）とProject（投稿個別）とOutputProfile（出力先）とAsset（素材実体）を分離する。
- テンプレート利用時の編集はテンプレートを暗黙に上書きしない。
- テンプレートの要素は安定したIDで追跡し、非表示・追加・削除・差分上書きに対応する。
- 不足したフォントや素材を勝手に別のものへ固定しない。代替プレビューは警告を出し、必要なら出力を止める。

## 2. テンプレートとバリエーション（REQ-TPL）
- ベーステンプレート：キャンバス、オブジェクト・レイヤーツリー、配置制約、フォント、効果、変数欄、パーティクル、再利用ロゴを保存する。
- バリエーション：色、ラベル、アイコン、効果、表示可否、必要に応じたレイアウト差分を保持する。ベースは変更しない。
- 個別プロジェクト：投稿ごとの文字列・画像・手直し・出力先固有の変更を保持する。
- 新規作成・編集・読み込み・複製・名前変更・削除・別名保存・複数バリエーションに対応する。
- テンプレートの更新に対し、個別プロジェクトへどの変更を伝えるかを明示できる設計とする。初期の安全な既定動作は「プロジェクト生成時のスナップショットを保存して暗黙同期しない」。
- 変数入力だけで完成し、必要に応じてオブジェクトを追加／削除できる両立が必要。

## 3. マルチサービス出力（REQ-LAY/REQ-EXP）
- 出力プロファイル：サービス名、キャンバス幅・高さ、縦横比、ファイル形式、セーフエリア、UI重なり領域、拡張メタ情報を持つ。
- サービス固有サイズ・OGP表示位置は固定の正解としてハードコードしない。確認日・根拠URLを併記した更新可能なプリセットとする。任意サイズのカスタムプロファイルも許可。
- x/y/幅/高さ・フォントサイズ・余白等の必要な数値に絶対値・相対値を選択できる。アンカーは9方向、基準はキャンバス／セーフエリア／親／他要素（後二者はルールの依存関係と循環チェックを持つ）。
- レスポンシブ変換時は制約を評価し、必要に応じてプロファイル専用の差分設定を持てる。勝手に破綻した配置を確定せず、衝突・はみ出しを可視化する。
- 出力先を複数選択し一括PNG書き出し。ファイル名にサービス・タイトル・連番・日付等の変数を使用可能。ファイル名の不正文字と重複を安全に処理する。
- セーフエリア・サービス側のラベル重畳表示は**編集ガイドのみ**とし、画像に焼き込まない。プレビュー上で切替・重ね表示できる。

## 4. 通常オブジェクトと操作（REQ-IMG/REQ-UI）
- テキスト、ラベル、画像、複数画像コンテナ、SVGアイコン、図形、パーティクル、グラデーション・エフェクトレイヤー、グループを扱う。
- 配置・回転・拡大縮小・不透明度・重なり順・表示・ロック・複製・削除・整列・スナップ・角丸半径（可能なものは四隅個別）を編集。
- PNG/JPEG/WebP等の画像をインポートする（ファイル形式の最終対応表は実装時に実機検証）。向き情報・ピクセル寸法を揃えて解釈し、元画像を保持。
- `contain` と `cover`、手動トリミング、画像を画像枠に自動フィット、位置・倍率・回転を指定可能。
- 一つの画像コンテナ内に複数画像を配置、均等整列、グリッド、横・縦・斜め分割に対応。
- **分割線は角度・位置を操作する直線**。縦横斜めは角度で表す。装飾なしの「透明な境界」と装飾あり（線色・幅等）を選べる。複数分割線から複数領域を扱う設計にする。
- スプリット内の各画像は独立して移動・トリミング・拡大縮小・回転・個別エフェクトを編集する。
- エフェクトは画像個別→クリッピング→分割線合成、または分割線を含めた合成後→エフェクト、という対象選択を可能にする。

## 5. 画像内のメタデータと構図の自動調整（REQ-CMP）
画像1枚に複数の**優先表示領域(keep)**と**優先除外領域(avoid)**を指定できる。領域は元画像の正規化座標に保存し、元画像は非破壊。矩形を基礎とし、円形・多角形を拡張可能な構造とする。領域の優先度、目標アンカー点、表示・除外の度合いも管理可能。

自動調整の目標は「keepを残し、avoidを外す」だけではなく、**元の構図における相対的位置・大きさ・はみ出し方向を、異なるアスペクト比でも可能な範囲で維持する**こと。例えば、右上から内側の顔、左下へはみ出す腰、右側へ傾けた人物という意図をできるだけ守る。

- モードA：回転角度を固定。位置(x,y)と倍率(s)を探索。
- モードB：回転角度変更を許可。位置(x,y)、倍率(s)、角度(theta)を、基準角度±ユーザー指定許容範囲で探索。
- keepの表示割合・位置ずれ・見かけの大きさ、avoidの表示割合・はみ出し方向、拡大率差、回転差、余白を条件として候補を評価する。必須条件と重み付き目標を分ける。
- 自動補正は**制作支援**であり必ずしも良好な構図を保証しない。採用された候補・評価理由をデバッグ表示し、候補切替、ユーザー手動補正、元の配置への復帰を可能にする。
- 自動補正結果と手動補正は出力プロファイルごとに保持し、元画像の領域メタデータと元の構図を上書きしない。
- 画像分割が多角形になっても各スロットの可視領域に対する評価ができる設計とする。

## 6. 文字とフォント（REQ-TXT/REQ-FNT）
- 日本語、英数字、記号、複数行、改行、文字間・行間・揃え、文字色・背景・縁取り・影・グラデーション・効果。
- 全文字列だけでなく、1文字ずつの円形背景などの装飾を**文字列が変わっても再適用**できる。グラフェム（見た目の1文字）とグリフの違いを考慮し、結合文字や絵文字を破壊しない。
- 文字全体の効果スタック：非破壊ぼかし、濃度・閾値・輪郭調整などを組み合わせた「すみだまり」をプリセット保存。文字列を差し替えても再計算する。
- タイトル・ラベル・番号・日付ごとに異なるフォントを指定。Google Fonts等のWebフォント、端末内で利用可能なフォント、ユーザーが取り込んだフォントファイルに対応。
- モバイルで端末フォントを**全部自動列挙できる保証はない**。環境で利用可能なシステムフォント指定と、ファイル選択によるインポートを提供する。
- フォントの読み込み完了・文字欠落・代替使用を診断でき、出力前に通知する。フォントライセンス情報を管理し、ファイル同梱を無条件に行わない。

## 7. ラベル、アイコン、装飾、素材（REQ-LBL/REQ-AST）
- 「全体公開」「成人向け」「支援者限定」「先行公開」「お知らせ」「作品」「更新情報」など一般的ラベルを初期搭載。使わない初期ラベルは**選択一覧から非表示**にできる（削除ではない）。独自ラベルの登録・編集・非表示も可能。
- ラベルは文字・背景色・半径・余白・枠・アイコン・装飾を一体で扱い、バリエーションで切り替える。
- 豊富なSVGアイコンを内蔵（ライセンスに従って帰属表示）。カラー・回転・拡大縮小・グリフ切替、テンプレート埋め込み。
- バナー全体とラベル等の装飾プリセット：紙、破れた紙、プラスチック、マスキングテープ、質感・影・光沢・ノイズ・形状など。標準プリセットに加えて独自プリセット保存・適用。
- 自筆サイン、印影、サークルロゴ、自作タイトルロゴ、象徴的装飾など、頻用素材を**メイン画像とは別の素材ライブラリ**へ保存し、再配置・テンプレート参照・必要に応じて埋め込みができる。
- 画像から主要色を抽出し、グラデーション・ティント・文字・帯・ラベル・アイコンへ配色。明度・彩度調整、コントラスト確認も提供。

## 8. 非破壊レイヤーと効果（REQ-FX）
- レイヤーツリーを表示し、並べ替え・グループ化・表示ON/OFF・ロック・複製・名前変更・ブレンドモードを管理。
- ぼかし、グラデーション、単色、ノイズを独立した**非破壊調整レイヤー**として扱う。テンプレートに保存し、下層の画像差替えにも自動で作用する。
- ぼかし対象：全面、矩形、円・楕円、角丸形状、マスク。中央から外縁に向けて弱くなる/逆転する可変ぼかし。マスク、ぼかし強度、フェザー、減衰カーブ等。
- グラデーションは線形・放射状、複数ストップ、形状・不透明度・反転などを持つ。
- ブレンドモード：Normal、Multiply、Screen、Overlay、Soft/Hard Light、Darken、Lighten等。描画結果がブラウザで同等になるよう試験する。
- レイヤー効果とオブジェクト固有効果を区別し、対象範囲（下層全体、グループ内、単一要素、コンテナ内部の画像／分割線／文字背景）を明示する。プレビュー・出力で処理順序が一致する。

## 9. パーティクル（REQ-PRT）
- パーティクルレイヤーをベーステンプレート・バリエーション作成時から追加して保存する。
- 光粒、雪、花びら、ほこり、火花、幾何図形等を、位置・数・速度・寿命・重力・揺らぎ・色・透明度・合成方法で設定する。
- 動作をプレビューし、任意の時刻／フレームを静止画に採用。同じシード・時刻・設定・出力条件では再現可能な結果を目指す。出力プロファイルごとの再配置にも対応する。

## 10. 変数・半自動入力（REQ-AUT）
- 投稿タイトル、サブタイトル、カテゴリ、公開区分、日付、連番を入力変数として定義し、1値を複数表示箇所へ連動。
- 日付書式を指定、手動上書き可能。連番はシリーズ別管理、接頭辞/接尾辞、ゼロ埋め、手動／自動加算に対応。
- 連番はプレビューや試しの出力で意図せず増えないよう、**採番確定のタイミングを明示**する。
- 変数をファイル名テンプレートにも使える。

## 11. 保存・移行・書き出し（REQ-DAT/REQ-EXP）
- ブラウザ内保存はIndexedDBを基本候補とする。画像・フォント等のBlobを識別子で参照し、重複を抑える。
- データスキーマ版とマイグレーションを設計し、旧データの読み込みとエラー復旧、エクスポート／インポートに対応。
- ZIP等にプロジェクトと必要な素材をまとめて外部バックアップできる。異なる端末への移行と、素材欠損時の説明を用意。
- 完成画像のPNG出力、プロファイル別一括出力、ファイル名自動生成、保存先選択ができない端末のフォールバックを提供。
- プレビューと書き出しの見た目をできるだけ一致させる。フォントの読み込み・画像処理の非同期完了前には出力を開始しない。
- ページの再読み込み、作業復元、Undo/Redo、取り消しできない操作の確認を考慮する。

## 12. デバッグ機能（REQ-DBG）
- 開発時からアプリ内診断モードを備え、通常の編集操作から容易に切り替えられる。
- 現在の選択・レイヤーツリー・アンカー・座標・行列・出力プロファイル・上書き元・解決後の値を可視化。
- 効果スタック／レンダーターゲット／画像分割領域／マスク／境界線の描画段階を可視化。
- 自動構図補正の入力、制約、各評価項目、候補、理由、適用前後の状態をログ記録。
- 失敗した非同期ロード、フォント不足、GPUコンテキスト喪失、保存容量超過、PNG失敗等のエラーを分類し、再現用診断ファイルをエクスポート。
- 診断ファイルには作品画像・署名・個人情報を**既定で含めない**。素材同梱は明示的な許可を要求する。ログには機微な文字列を不要に収集しない。
- 描画時間、メモリ推計、テクスチャ数、操作履歴、プレビュー／出力差分を表示。診断機能はオフにできる。

## 13. 対応環境と品質（REQ-UI/REQ-SEC）
- 主要環境：iOS Safari・Android Chrome。PC Chrome/Edge/Safari/Firefoxも確認対象。実機のOS・ブラウザ・GPUをテスト結果に記録。
- 指での選択、移動、ピンチ拡大、回転ハンドル、長押し、誤操作防止、タッチ領域、狭い画面の折りたたみパネル。
- モバイルメモリ不足、OSの中断復帰、画面向き変更、GPUコンテキストロスト、ダウンロード制限などの異常系を扱う。
- SVGのサニタイズ、危険なHTML混入防止、画像URLのCORS、Canvas taint、ローカル情報の外部送信防止、外部素材の利用規約確認。
- UIの可読性、操作可能領域、文字色コントラストを考慮する。作品バナー自体への配色警告は提案であり強制改変しない。

## 14. 一括開発方針と完成の定義
**開発方法：全体実装先行型。** AIが開発内部で設計・小さなコミット・単体テスト・E2Eテスト・修正を回すのは必須だが、利用者には小機能単位の逐次承認を要求しない。初回の提出は全体UIと主要ワークフローを通せる一体型アプリを目標とする。

機能未実装、仮のUI、代替実装、テスト未完、端末未検証は明示し、全件のREQ-IDと紐づける。画面が存在するだけで「実装済み」と判定しない。実機で未確認の機能は「実装済・実機未確認」等と記録する。

受け入れは、(1)要件→実装箇所→テスト結果の追跡、(2)保存と復元・一括出力の完走、(3)診断と再現、(4)モバイル実機検証、(5)既知の重大な不具合の明記を条件とする。詳しくは `05`、`09`、`10` を参照。


# Ver.0.3追補：開発環境・保存・公開段階・運用（利用者決定事項）

- **端末の実機検証**：利用者が動作確認に使用できるのはiPhone/iPadであり、iOS Safariを本人検証の主対象とする。Android ChromeやPC向けの互換性要件は維持するが、本人の実機がない環境の実績を偽らない。
- **保存**：プロジェクト・テンプレート・素材を端末ブラウザ内に保存し、バックアップファイルのエクスポート・インポートを提供する。初期版のアプリデータをクラウド同期することは要求しない。
- **公開段階**：開発開始後は本人しかアクセスできないテストサイトを利用し、完成に近づいたら知人のみを招待したβテストを行う。一般公開はその後の別途判断とする。
- **アクセス方針**：GitHub Freeの公開リポジトリからGitHub Pagesで公開。本人中心のテスト期・知人β期とも公開サイトとし、アプリの入口にクライアント側の簡易パスワード入力画面を置く。これは厳密な認証ではなく閲覧やソースの秘匿は保証しない。外部ホスティングは使用しない。サイト初回デプロイ・β案内・一般向け告知はそれぞれ明示承認。
- **開発操作の支援**：GitHub操作を利用者に求める場合は、具体的なiPhone/iPad向け日本語手順をその都度案内する。
- **開発進行**：初回のAI開発では統合アプリ全体を目標とし、以後は対象モジュールを分離して改修・テスト・統合する。UI変更はモックで確認してから統合する方針。
- **承認境界**：開発開始、GitHub接続・権限付与、初回デプロイ、β招待、一般公開、外部サービスへの素材送信は、別途明示承認があるまで実施しない。
