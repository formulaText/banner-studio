# 開発後の検証計画・確認項目書作成手順
版：0.2／2026-11-05　注：初回実装後に**実コードと実画面を読んで確定版を生成**すること。レビュー追加の具体試験は`21_品質ゲートと受入判定.md`を参照し、`10`へ統合済み。

## 1. 検証の目的
「全機能があるように見える」状態と「要件を満たす」状態を区別する。各要件について、実装箇所、操作手順、期待結果、自動テスト、実機での観察、診断出力、既知制約を記録する。UIだけのプレースホルダー、擬似処理、テスト未実施は合格扱いにしない。

## 2. 成果物
- `verification/requirements_coverage.csv`: 09を複製し `implementationFiles`, `status`, `testIds`, `evidence`, `issues` を追記。
- `verification/checklist.csv`: 10を基に、実画面の操作名・ステップ・期待値・診断操作・デバイス欄を補強。
- `verification/test-results/`: 自動テスト報告、スクリーンショット差分、ログ、再現ZIP（素材は必要最小限）。
- `verification/known-issues.md`: 影響度・再現条件・診断ZIP・原因・暫定回避策・修正コミット。
- `verification/acceptance-report.md`: 未実装／未確認／既知重大不具合を含めた集計と判断。

## 3. 検証状態（混同禁止）
- `未実装`：UIがない、または実処理がない。
- `仮実装`：操作はできるが要件が満たせない／ダミー動作。
- `実装済・未試験`：コードはあるが検証証拠がない。
- `自動試験合格`：ユニット／E2E等で合格しログがある。
- `実機合格`：対象実機で操作して合格し記録がある。
- `不合格`：期待値と異なる。
- `環境制約`：仕様・ブラウザ制限による未達、代替策と利用者通知を記録。

## 4. 確認項目書の生成手順
1. 要件マスター`09`を全件読み込み、各REQ-IDの実装関数・UI導線を探して紐づける。見つからなければ「未実装」。
2. 要件の肯定系、境界値、異常系、他機能連携を最低1件ずつ検討。初期一覧`10`を補強し、新たなケースは`TC-***`等のIDで採番する。
3. 確認項目に**どのUIで何を操作するか**、使う素材のID、期待される値・画像状態、診断画面で見るフィールドを記載。
4. 自動テストにできる項目はVitest/Playwrightに実装し、テストファイルのパスを記録する。実機専用はその理由を記載。
5. 対応端末を割り当て、iOS Safari・Android Chrome・PC Chrome/Edge/Safari/Firefoxで検証対象を分担。再現に必要な端末／OS／ブラウザ版を保存。
6. 初回検証後、不合格の再現ZIPとスクリーンショットを診断機能から作り、問題管理台帳を作成する。
7. 修正ごとに直接ケース＋関連機能の回帰ケースを再実行。合格への変更には証拠が必要。

## 5. テストレイヤー
### 5.1 静的検査
TypeScript型検査、リンター、バンドル作成、依存ライセンス・脆弱性チェック。構文だけでなく未到達コード・未接続ボタンも確認。

### 5.2 単体試験
- レスポンシブ単位換算、アンカー、循環参照、角丸、分割ポリゴン、変換行列、keep/avoid面積。
- 自動補正：角度固定なら厳密に同値、角度許可なら上限内、候補評価の一貫性、目標点位置、手動override尊重。
- テンプレート差分と原本不変、バージョン移行、日付・連番・ファイル名、シード再現。

### 5.3 統合試験
- 画像取り込み→配置→装飾→保存→再読込→複数プロファイル出力。
- 画像スプリット→個別FX→線装飾→グループFXの順序。
- フォント読込成功/失敗→プレビュー/書き出し。
- 診断ZIP→再現セッション、バリアント／Project差分と出力先override。

### 5.4 UI/E2E試験
PlaywrightでPCエミュレーション・モバイルビューポートの一般操作とダウンロードを自動化。**エミュレーションはiOS Safari実機検証の代わりではない**。タッチのつまみ・ピンチ・OSファイル保存は実機手動テストを追加。

### 5.5 画像の視覚比較
- golden画像：基本テキスト、図形、画像、斜めスプリット、文字単位円形背景、グラデーション、可変ぼかし、粒子フレーム。
- 同一OS・同一ブラウザ・フォント・GPU条件でベースラインを作成し、差分・閾値を管理。見た目が変わる変更にはレビューログを付ける。
- スクリーンショットの微差だけでは失敗扱いにせず、機能上の値・表示結果と組み合わせて判断する。

### 5.6 実機試験
主要端末にiOS SafariとAndroid Chromeを含める。最低でも代表的なiPhone・Android各1台＋PC。OSバージョンを記録。横向き/縦向き、画面サイズ、バックグラウンド復帰、重い画像、保存・ダウンロード、フォントの失敗、オフライン条件を確認。

## 6. 組み合わせ検証（必須）
単体機能の成否だけでなく、次をシナリオで検証する。

**シナリオS1：基本投稿**
新しいTemplate→複数Variant→タイトル/メイン画像→出力先3種→セーフエリア確認→調整→PNG一括出力→再起動→再出力。

**S2：構図補正**
横長で顔keep・腰avoid・右倒し→正方形/縦長→角度固定/許可切替→候補を比較→手動override→元画像の領域が不変であること。

**S3：画像と効果**
複数画像→斜め分割→各画像回転/拡大→個別ぼかし→線なし/あり→グループぼかし→書き出し、線のシャープさを確認。

**S4：文字効果**
日本語Webフォント→一文字円形背景→字間・行間→すみだまり→本文差し替え→PNGへ同等に反映。

**S5：素材・バリエーション・パーティクル**
ロゴをライブラリへ→テンプレ埋込→Variantで配色・粒子を変更→シードとフレーム固定→別Projectでも再現。

**S6：保存/障害**
保存後の強制リロード→正常復旧。画像欠落・フォント404・DB容量不足・コンテキスト喪失・不正JSON→適切な警告、デバッグZIP、元データ非破壊。

## 7. バグ管理
各問題を `BUG-0001` 等で識別。状態 `new / reproduced / investigating / fixed / verified / deferred / won't-fix(with reason)`。重大度は `S0:データ破損/漏えい`, `S1:主要フロー不可`, `S2:主要機能不良`, `S3:回避可能な軽微不具合`。

バグ記録に最低限必要：REQ-ID、TC-ID、端末・ブラウザ、操作手順、期待結果、実際の結果、診断コード、再現ZIP（必要なとき）、修正コミット、再試験結果、再発防止テスト。

## 8. 合否判断
- **テストが通らなかった**項目と、**テストを実施していない**項目を別集計にする。
- 初回提出時の受入：全REQに実装状態を付与、主要シナリオS1/S2/S3を操作可能、診断ZIPと保存復元を実証。全機能の合格を初回提出の前提として虚偽申告しない。
- 目標完成時の受入：S0/S1未解決0件、全REQの実装根拠がある、主要モバイル実機でシナリオ合格、既知制約と後回しを明示。S2/S3の残件は承認記録を残す。
- 完成の判定はユーザーが行う。AIは証拠と未達一覧を提出する。


# Ver.0.3補足：本人実機と段階的βの検証計画

## 検証担当の区分
- 利用者本人：iPhone/iPadのSafariで実操作、画像・文字・バックアップ・PNG出力・UI確認を担当。
- 開発AI：単体テスト、PC/シミュレータE2E、静的解析、ビルド、再現可能な画像比較を担当。
- 招待βテスター：本人の許可後に、使い勝手・異なる端末／データ条件・実制作の報告を行う。デバッグZIP提供は任意。
- AndroidとPCの実機を利用者が保有しているとはみなさず、外部テスター・提供された環境で検証した事実のみ記録する。

## 本人中心のテスト運用→知人βへ移行する条件
- 本人のiPhone/iPadで認証、編集、保存、読み戻し、PNG、バックアップの出力と読み戻しを実施済み。
- 重大なデータ破損／外部公開漏れが未解決でないこと。
- 公開用ソース／アセットに秘密情報が入っていないこと、HTTPS・保存復元・未公開素材の無断外部送信がないことを確認する。URLは他者もアクセス可能で、アクセスの撤回は保証されない旨をβ参加者に説明する。
- 参加者向けの既知不具合・バックアップ手順・フィードバック様式が準備済み。
- 本人が知人β段階への移行を明示承認していること。

## βテストの報告・修正の流れ
テスター報告をBUG-IDにまとめ、要件・TC-IDに紐づける。機能の修正は対象モジュールのブランチで実施し、確認済みのデザインモックと統合時の回帰試験を通してからβへ再配信する。未検証環境で「合格」と記載しない。
