## 1. ミッション
添付された`docs/`一式を読み込み、iOS Safariを本人実機の主対象とし、Android Chrome・PCにも対応とする**テンプレート駆動・マルチサービス投稿バナーWebアプリを、一度の開発キャンペーンで全体実装する**。実装初期から診断機能とテストを組み込み、動作する統合アプリを成果物として提出する。ユーザーに小機能ごとの許可を求める開発方式は避け、内部で計画・実装・テスト・修正を回す。

ただしツール／コンテキスト／実行時間には限界がある。無理な「全機能完成」の宣言を避け、未完の箇所は明確に報告して引き継ぎ可能な状態を残す。セッションをまたぐ場合は`HANDOFF.md`に再開手順を保存する。

## 3. 動作環境・技術方針
- TypeScript/Vite。UIとドキュメントモデル・描画器・最適化器を分離。
- 第一候補PixiJS v8 + WebGL2。ローカル端末・許諾・実機で不可と確認した場合は代替案を調査し、変更理由を記録。
- IndexedDB/Dexie等で永続化。ZIP外部バックアップ。ユーザーのメイン画像・サインはクラウドへ無断送信しない。
- OpenCV.jsは必須依存にせず、非AIの構図幾何最適化から始める。
- 外部ライブラリのバージョンを取得して固定し、ロックファイルとライセンス一覧を納品。

## 4. 開発の進め方（ユーザーへの分割納品は必須でない）
①環境構築とフォルダ/型/スキーマ/テスト基盤。②縦断的な最初の編集→保存→出力→診断ループ。③残る全機能をREQ-IDに沿って組み込み、各モジュールを単体/結合テスト。④E2Eと画像差分、異常系、負荷測定。⑤実装済み/未実装/代替/未試験を一覧化し統合版を納品。

内部では動く状態でこまめにGitコミットし、完了機能が後の機能追加で破壊されないよう回帰テストを実行する。Gitを利用できなければ差分バックアップを保持する。

## 5. 絶対に省略してはいけない点
- 実際の機能がないダミーボタンや設定だけの機能を完成扱いしない。
- 文字装飾・高負荷エフェクト・粒子・回転付き構図補正について、機能を丸ごと削除するのではなく実現を試み、制限を明示する。
- テンプレート、Variant、Project、Profile、Assetの分離・原本非破壊を守る。
- UIから診断機能へアクセス可能にし、診断ファイルを既定で素材なしにする。
- 自動調整でkeep位置・avoid方向・回転角度制約・手動補正を扱う。
- モバイル主対象のため、PCマウス専用UIで完了と宣言しない。
- iOS Safari実機にアクセスできない場合は「未検証」と明記する。シミュレータやPlaywrightの結果を実機合格と呼ばない。

## 6. 選択基準
- 出力結果が決定論的で再現可能であることを優先。GPUによる近似差異は診断で記録。
- 設定値（仕様上のルール）と描画結果（ビュー）を分離。場当たり的なCanvas状態を保存データの正本としない。
- 描画ライブラリを複数重ねる場合はAPI境界・コストを説明。単に多機能に見せるための混在を避ける。
- 実装困難なら「制約→試した方法→代替候補→今の状態」を`implementation-gaps.md`に記録。

## 7. 必須の成果物
```

app/tests/                # 単体、結合、E2E、画像比較
app/fixtures/             # サンプルデータ（著作権確認済）
verification/             # 要件対応、確認項目書、実施記録
verification/known-issues.md
BUILD_REPORT.md           # 起動・ビルド・実装状況・性能/制約・未実装一覧
HANDOFF.md                # 中断時の再開手順、最後の成功コミット
licenses/                 # 依存・フォント・アイコンのライセンス一覧
```

## 8. 自動テストの最低条件
- `typecheck`、`lint`、`unit test`、`build`を成功させる（失敗の場合は理由と未修正記録）。
- 横長→正方形の自動構図補正の固定/許可モード、keep/avoid、上限角度、画像ごとの分割線エフェクト、保存復元、描画段階、フォントロード失敗、診断ZIPの匿名化を試験。
- PCのE2EはUIから新規Template→Variant→Project→3プロファイルPNG書き出しまで。
- テスト合格の主張には実行コマンド・件数・日時・出力ファイルを伴わせる。実行できなかったものは「未実施」。

## 9. 検証資料の生成
初回実装**完了後**に、実コード/画面/テストを読み、`09`と`10`を再照合した`verification/requirements_coverage.csv`と`verification/checklist.csv`を作成。REQ-IDを消さない。機能が未実装でも確認項目から除外しない。画面上で押すボタン名、操作経路、診断欄、期待値、対応端末、証拠パスを具体的に書く。

## 10. 報告形式
毎回の納品時に(1)起動方法(2)実装・未実装・制限のREQ-IDリスト(3)テスト結果(4)実機結果(5)既知の重大不具合(6)診断・再現方法(7)コミット/バージョン(8)次の修正候補を報告。

AIは結果が出るまで無期限に動く保証はない。実行環境に機能制約がある場合は代替案と再開方法を残し、ユーザーに「待てば後で完了する」と伝えない。
