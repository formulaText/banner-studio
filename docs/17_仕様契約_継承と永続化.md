# 実装仕様契約A：テンプレート継承・変更履歴・保存

版：0.2／2026-11-05　**開発AIが迷ったときに参照する暫定の動作規則**。本書の決定はユーザーの要件を削らない。

## 1. 用語
- **Template**：独立した原本。レイヤーID、配置規則、変数定義、素材参照、スタイル、パーティクル、効果を保存。
- **Variant**：Template IDと原本バージョンに紐づく上書き差分。色・ラベル・アイコン・表示等を変更可能。必要なら配置差分を持てる。
- **Project**：投稿1件の作業データ。生成時点のTemplate/Variantの**スナップショット**、入力変数、作業パッチ、出力別パッチを持つ。
- **OutputProfile**：出力先と利用目的（例：FANBOX投稿カバー、Xリンクカード）を識別するサイズ・制約・セーフエリアの定義。サービス名だけで一意にしない。
- **Asset**：ユーザーが読み込んだ画像・ロゴ・サイン・フォント・テクスチャのBlobとメタデータ。AssetRevisionも識別可能にする。
- **Layer/Node**：IDを持つ編集要素。重なり順は配列順／明示orderのどちらか一つで統一し、型変換時も維持。

## 2. Project作成の規則
1. 対象Templateの有効なバージョンを読み、スキーマ検証する。
2. 選択されたVariantがTemplate ID／バージョンと互換であることを検証する。
3. Templateの完全な編集用スナップショットと選択Variant差分のスナップショットをProjectに保持。元のTemplateへの読み取り参照IDも残す。
4. ユーザー入力（タイトル・メイン画像・日付など）はプレースホルダーへバインドし、原本を変更しない。
5. Projectでの追加・削除・スタイル変更はProjectPatchに記録し、Template・Variantを自動更新しない。
6. 既存ProjectでVariantを変更した場合、Projectが持つTemplateスナップショットに対して新しいVariantの**明示的適用**を行い、競合を表示する。旧作業状態をUndoできる。

## 3. 正規の適用順序
```
Template snapshot
  → Variant snapshot patches
  → Project共通の内容・スタイル・配置パッチ
  → (各OutputProfileで)単位解決・レイアウト・構図補正
  → Profile固有の属性パッチ（最優先）
  → 検証された描画ツリー
```
- `Project共通`はすべての出力先へ適用。`Profile固有`は指定先にだけ適用する。
- プロファイル固有の `x`,`y`,`scale`,`rotation` を持つときは、それを構図最適化の再実行で黙って上書きしない。明示的な「自動再調整」を選ぶ必要がある。
- Variantで属性を削除する場合と、文字列を空にする場合と、ノードを削除する場合を区別する。
- 同一属性への後段パッチは前段を上書きするが、ユーザーに出所（base/variant/project/profile）を確認できるようにする。
- レイアウト後の座標は**計算結果であってソースモデルではない**。再度デザイン変更する際は計算前の値を正本にする。

## 4. Patchの契約
Patchは `op: add|replace|remove|move|hide|show`、`targetNodeId`、型付きパス、値、対象scope、作成時の元Revisionを持つ。
- ノード追加は新規IDを生成。IDを別ノードに再利用しない。
- ノード削除はProject内のtombstone（削除状態）として記録でき、Templateの同IDを破壊しない。Undoで復元可能。
- 属性の差分削除（overrideの解除）と、オブジェクト自体の削除は異なる操作とする。
- すでに削除されたノードへの属性パッチは無視せず、競合ログに記録してユーザー操作へつなぐ。
- 親子参照の循環、ID衝突、欠損Asset参照、型不一致、存在しないプロファイルを検出する。
- パッチを適用する前後にスキーマ検証し、失敗した操作ではドキュメントに一切の部分変更を残さない。

## 5. 作業履歴と自動保存
- ユーザー操作1回を**Undo/Redoの原子コマンド**として扱う（例：レイヤー移動、分割線回転、複数画像取り込み）。連続ドラッグはジェスチャー完了時に1コマンドへ集約可能。
- Undo履歴と永続化済み状態の境界を明示。IndexedDBの保存は成功したトランザクションだけを「保存済み」と表示する。
- 保存失敗、容量不足、タブ中断時は「未保存／保存失敗」を表示し、元Projectを読める状態に保つ。
- アプリのバージョンアップでは旧データを読み取り専用で検証→コピーして変換→検証成功なら切替。失敗時に元データを失わない。
- IndexedDBの**全データ消失可能性**を前提とし、端末外ZIPバックアップ導線を実装。自動保存≠バックアップ。

## 6. Asset IDと画像メタデータの帰属
- 原画像BlobはAsset ID・Revision・SHA256で識別。ファイル名だけを同一性の根拠にしない。
- 元画像の正規化keep/avoid領域は、その画像の内容に紐づくメタデータとして保存し、同一素材を別バナーへ再利用可能。
- **配置インスタンスの**回転角度・位置・画像枠・元構図スナップショット・構図アンカーはProject/Templateの該当image-slotに保存。Assetへ書き戻さない。
- 同一画像が2箇所に配置された場合、keep/avoidは共有できる一方、個別の構図アンカーや優先度の上書きは分離可能にする。
- 同じSHA256のAsset取り込み時に重複警告または統合を行う。異なる見かけのファイル名だけでBlobを重複保存しない。
- Assetを更新するときは新Revisionを作り、すでに存在するProjectの画像を暗黙に置換しない。明示的な「参照先の更新」を提供する。

## 7. バックアップZIP・インポート
- 仕様候補：`manifest.json`（formatVersion、生成日時、ファイル一覧、長さ/sha256、参照関係）＋`data/*.json`＋`assets/*`。大容量・低メモリ機ではストリーミング実装を検討。
- バックアップ対象を「構造のみ」「必要素材を含む」に分ける。ライセンス未確認フォント等を自動同梱しない。
- ZIP読み込みは安全な一時領域で展開前ヘッダ・ファイル件数・圧縮後／展開後の上限・パストラバーサルを検証する。
- JSONはホワイトリスト形式のスキーマ検証を行い、プロパティ経由でのコード実行・外部通信・動的importを許さない。
- ID衝突時の既定は「別IDで複製して取り込み」。上書きは差分プレビューと確認後に限定。
- 素材欠損時は欠損IDと影響レイヤーを提示し、未確認の代替素材を自動確定しない。
- 途中で失敗したインポートはユーザーの既存Template・Projectを変更しない（原子性）。

## 8. 連番と出力の整合
- プレビュー・診断・試しのPNG出力では連番カウンタを進めない。
- 正式出力時に連番候補を予約し、全選択プロファイルの出力処理が成功した時だけ確定する暫定方針。失敗があれば予約を解除し、出力済みファイルは再出力できる。
- 同じProjectの再書き出しは既存の確定番号を再利用。明示的な「次番号へ進む」操作でのみ新番号を採る。
- 並列タブ・複数出力要求の競合はIndexedDBトランザクションで排他／再試行・エラーにする。
- プロジェクトの日時は指定タイムゾーンで計算。自動日付更新のタイミングは新規作成・明示更新を基本とし、既存バナーを再出力したとき勝手に変えない。

## 9. 実装完了と呼ぶためのテスト
- Variantでカラーを上書き→Projectで再上書き→Profileごとに位置だけ変更→再読込で一致。
- Template更新後にも既存Projectの見た目が暗黙に変わらない。
- 画像を2箇所で再利用して、keep/avoidは共有し構図アンカーは別々に保持。
- ノード削除とOverride解除の違い、競合時の明示エラー。
- ZIP途中失敗・容量不足・ID衝突時でも元データを破損しない。
- 正式出力失敗・再出力・並列タブで連番が不当に増えない。


# Ver.0.3追加：端末ごとの保存・バックアップ契約

- 端末内データはブラウザのオリジンに依存し、同じGitHubリポジトリのデプロイであっても配信URLが異なれば同一保存域とはならない。
- iPhone→iPad、iPad→iPhoneの移行は、明示的なバックアップファイルのエクスポート／インポートを通じて行う。自動同期を実装済みと表示しない。
- バックアップにはスキーマバージョン・アセットの整合情報・参照元のオリジン識別情報（秘密ではない）を記録できるようにする。
- β版で新しいスキーマを配信する際は、既存の利用者データを保護し、必要なら旧版からの移行処理をテストする。
