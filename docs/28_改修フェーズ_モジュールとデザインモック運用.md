# 一括開発後の検証・修正・統合運用

版：0.3／2026-11-06。初回は全体を一括開発し、**初回版の完成後**は対象機能を切り出して改修する方針。

## 1. 基本サイクル
1. 本人またはβ参加者が不具合／改善要望を登録（BUG-ID, REQ-ID, TC-ID, 端末・再現手順）。
2. 安定動作する統合版にタグ・バックアップを付け、修正用ブランチを分ける。
3. 対象モジュールの仕様契約（入力・出力・データスキーマ・イベント）と関連テストを確認する。
4. 単体のプレビュー画面／実験用デモで変更を実装し、機能・視覚品質・性能を検証する。
5. UIやデザイン変更の場合はモックで本人が確認し、修正の方向を決める。
6. テストに合格した変更をプルリクエストなどで比較し、統合版へ取り込む。
7. 関連する機能の回帰テスト、データ読み戻し、iOS Safari動作を確認し、問題があれば統合を取り消す。
8. 仕様や検証項目・診断ログを更新し、確認済みの版を本人が利用する公開テスト環境／知人にURLを案内したβ環境へ配信する。配信は公開範囲の承認条件を守る。

## 2. モジュール分割単位の候補
- 画像・スプリットレイアウト／マスク
- 自動構図補正（幾何計算と候補スコア）
- 非破壊効果（ぼかし、調整レイヤー、ノイズ）
- テキスト、文字単位装飾、すみだまり
- テンプレート継承／バリエーション
- IndexedDB／ZIPバックアップ／復元
- 出力プロファイル／PNG生成
- モバイルUI／操作ハンドル

## 3. デザインモックの運用
- 「レイヤーパネル」「トリミング設定」など画面／操作単位のモックを先に作成する。
- 実際のiPhone/iPad上で、タップしやすさ、文字入力、スクロール、画面回転、狭い表示幅を確認する。
- モック承認後に本来のモデル／レイヤー機能へ接続する。モックを本番機能と偽って報告しない。
- 見た目のレビューとプログラムの品質ゲートを別々に記録する。

## 4. 統合時に破壊してはならない契約
- REQ-IDや保存データのID／スキーマを無断変更しない。必要なら移行処理と旧データ試験を追加する。
- テンプレート原本と作業プロジェクトの独立性を維持する。
- 1モジュールのテストが通っても、統合レイヤー・エフェクト・PNG出力が変わる場合は全体の画像比較を実施する。
- 日付・連番・パーティクルなどの再現性を崩さない。
- デバッグ機能・ログ出力を回帰試験から外さない。
- β公開済み環境では破壊的変更前にデータ移行とバックアップの案内を準備する。

## 5. 改修完了の証拠
修正対象のBUG-ID、変更されたファイル、テスト結果、画像比較、診断ログ、実機検証状態、Git履歴／プルリクエスト、リリース先と公開範囲をまとめて記録する。AIの「修正しました」という文章だけを合格根拠としない。
